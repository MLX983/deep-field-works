# Deep Field Works — Domain Structure

## Purpose of this document

This document defines the working domain structure for Deep Field Works.

In this context, “domains” are not web domains.

They are broad thematic territories for organizing the site’s ideas, notes, essays, experiments, prototypes, concepts, and checkpoints.

The goal is not to create a rigid taxonomy.

The goal is to give the site enough structure that ideas can accumulate over time without becoming scattered.

Domains should remain broad enough to survive changes in emphasis.

The content inside each domain may evolve, but the domain names should continue to hold the larger inquiry.

---

# Why domains are needed

Deep Field Works is intentionally exploratory.

It will include:

* essays
* notes
* prototypes
* project logs
* field reports
* concept documents
* checkpoints
* future video seeds

A purely chronological index is useful because it preserves development over time.

It shows:

* when ideas appeared
* how language changed
* which concepts were primitive at first
* how the project accumulated
* where assumptions shifted

But chronology alone has a weakness.

It makes every reader start from time.

Domains provide another path.

They let a reader ask:

* What is this project mostly about?
* What ideas are connected?
* Where should I start if I care about AI and work?
* Where are the interface prototypes?
* Where are the larger institutional arguments?
* Where are the notes about memory, media, and archives?
* How has thinking on a topic evolved?

The best structure is likely:

```text
Index       = chronological field log
Domains     = thematic territories
Types       = artifact forms
Checkpoints = periodic syntheses
Concepts    = durable vocabulary
```

This preserves history without forcing new readers to navigate only by date.

---

# Domain vs. type vs. theme

Deep Field Works should separate three classification layers.

```text
Domain = what larger territory the piece belongs to
Type   = what kind of artifact the piece is
Theme  = what recurring cluster or topic the piece connects to
```

Example:

```text
Title: The Pyramid Was Built to Route Information
Domain: Institutions in Transition
Type: Essay
Theme: organizational-redesign
```

Another example:

```text
Title: Monitoring Preferences
Domain: Interfaces for Judgment
Type: Experiment
Theme: supervision-interfaces
```

This prevents the site structure from becoming confused.

“Field note” is a type, not a domain.

“Agent governance” is a theme, not necessarily a domain.

“Human-Machine Workflows” is a domain because it describes a broad territory that can hold many types and themes.

---

# Naming principles

Domain names should be:

* broad enough to hold future work
* specific enough to imply a point of view
* plain enough to be understandable
* distinctive enough to feel like Deep Field Works
* durable enough not to depend on current AI news
* flexible enough to contain notes, essays, prototypes, and checkpoints

Avoid names that are too narrow.

For example:

* “AI Agents” may become dated or too tool-specific.
* “Prompt Engineering” is too narrow and already culturally loaded.
* “Future of Work” is too generic.
* “Productivity” points in the wrong direction.
* “Automation” is too mechanical by itself.
* “Design for AI” sounds too much like a portfolio category.

Prefer names that describe deeper patterns:

* how cognition is externalized
* how work changes when systems act
* how institutions reorganize around shared memory
* how interfaces mediate judgment
* how public ideas develop from private notes

---

# Recommended domain set

The recommended starting structure is five primary domains:

1. Cognitive infrastructure
2. Human-machine workflows
3. Institutions in transition
4. Interfaces for judgment
5. Media, memory and meaning

These five are broad enough to hold the current launch material and flexible enough to evolve.

They map to the larger purpose of Deep Field Works: understanding how AI, design, media, institutions, and human judgment change each other over time.

Together, they create a coherent map:

```text
Thinking changes.
Work changes.
Organizations change.
Interfaces change.
Media and memory change.
```

That is the larger Deep Field Works territory.

# 1. Cognitive Infrastructure

## Working description

How thinking, memory, research, writing, and decision-making change when cognition becomes partly externalized into tools, archives, models, agents, and personal knowledge systems.

## Why this domain exists

This may be the deepest root of the project.

Deep Field Works is not only about AI as a tool.

It is about what happens when cognition becomes distributed across:

* people
* machines
* notes
* archives
* retrieval systems
* generated artifacts
* recurring models

This domain holds the “thinking about thinking” layer.

It includes the idea that a knowledge base can become more than storage.

It can become a recursive system that helps generate new work.

## What belongs here

This domain can include pieces about:

* externalized cognition
* personal knowledge systems
* recursive archives
* memory versus storage
* RAG and retrieval as thinking infrastructure
* notes becoming essays
* essays becoming checkpoints
* checkpoints becoming future scripts or prototypes
* how AI changes reading, writing, synthesis, and reflection
* how human judgment changes when memory is searchable and generative

## Possible artifacts

* Essay: “The Archive Becomes Part of the Work”
* Note: “Storage Is Not Memory”
* Field report: “What Changes When the Knowledge Base Can Write Back?”
* Checkpoint: “Current Model of Personal Cognitive Infrastructure”
* Project log: “Building Deep Field Works as a Recursive Knowledge System”

## Why the name works

“Cognitive Infrastructure” is broad, durable, and serious.

It does not lock the site into a specific technology.

It can hold AI, notes, search, archives, writing systems, memory, and long-term creative workflows.

The risk is that the phrase may feel abstract.

That is acceptable if the domain page explains it clearly with concrete examples.

## What this domain should avoid

Avoid turning this into generic personal knowledge management content.

This is not about:

* note-taking hacks
* app comparisons
* productivity systems
* second-brain aesthetics

The deeper question is:

> What happens when the materials of thought become structured enough to participate in future thinking?

# 2. Human-Machine Workflows

## Working description

How people and AI systems divide labor, coordinate action, supervise automation, and create new forms of work together.

## Why this domain exists

This is the practical layer of the AI question.

AI adoption is often discussed in terms of tools or productivity.

The more interesting question is how work changes when tasks, judgments, and actions are distributed between humans and machines.

This domain holds pieces about:

* delegation
* supervision
* control
* review
* agentic workflows
* changing knowledge work
* human-in-the-loop and human-on-the-loop systems

## What belongs here

This domain can include pieces about:

* agents acting on behalf of users
* human review loops
* AI-assisted drafting and sending
* monitoring preferences
* alert governance
* task delegation
* approval flows
* supervision of autonomous systems
* AI-generated recommendations
* failure modes of automation
* what work remains human

## Possible artifacts

* Essay: “Delegation Is Not Abdication”
* Prototype note: “Monitoring Preferences”
* Prototype note: “Agent Message Review”
* Field report: “When AI Starts Taking Action”
* Essay: “The Human Role Moves Upstream”
* Checkpoint: “Current Model of Human-Machine Workflows”

## Why the name works

“Human-Machine Workflows” is clear and flexible.

It includes AI without making the domain name dependent on AI terminology.

It also makes the domain practical: this is where work is redesigned, not just theorized.

The phrase can hold both enterprise product design and broader questions about how people cooperate with systems.

## What this domain should avoid

Avoid becoming a collection of AI tool tips.

The focus should not be:

* how to use this app
* best prompts for productivity
* top AI tools for work

The focus should be:

> How does the workflow change when part of the work can be performed, interpreted, or initiated by a system?

# 3. Institutions in Transition

## Working description

How organizations, hierarchies, governance systems, management roles, and institutional memory change when AI alters the flow of information and authority.

## Why this domain exists

AI does not only change individual tasks.

It changes the structures around those tasks.

Many organizations are trying to add AI to systems built for a different era: systems where information had to be collected, translated, summarized, routed, escalated, and approved by people.

If AI changes the routing of information, the organization around that routing may also need to change.

This domain holds the larger institutional questions.

## What belongs here

This domain can include pieces about:

* the organizational pyramid
* middle management changing but not disappearing
* shared context
* approval routing
* institutional memory
* governance
* authority and delegation
* organizational redesign
* bureaucracy and automation
* decision latency
* coordination overhead
* how AI affects management work
* how companies capture or miss AI ROI

## Possible artifacts

* Essay: “The Pyramid Was Built to Route Information”
* Essay: “The Middle Layer Changes, But Does Not Disappear”
* Field report: “AI Adoption Inside the Old Org Chart”
* Checkpoint: “Current Model of AI and Institutional Memory”
* Essay: “The ROI Is in the Structure Around the Tool”

## Why the name works

“Institutions in Transition” is broader than “AI at Work” or “Future of Work.”

It can include companies, teams, management systems, public institutions, schools, and governance structures.

It also avoids overcommitting to one conclusion.

The institutions are changing, but the shape of the change remains under observation.

That fits the Deep Field Works posture: strong enough to name the pattern, humble enough not to pretend the outcome is settled.

## What this domain should avoid

Avoid generic future-of-work commentary.

Avoid broad claims like:

* AI will flatten organizations
* middle managers will disappear
* companies must adapt or die

The better approach is more operational:

> Which routing functions become less necessary? Which judgment functions become more important? Where does authority move? What new supervision burden appears?

# 4. Interfaces for Judgment

## Working description

How interfaces can help people interpret signals, manage uncertainty, supervise systems, and make better decisions when conditions are ambiguous.

## Why this domain exists

This domain connects product design practice with the larger Deep Field Works inquiry.

Many AI and automation problems are not only model problems.

They are interface problems.

When a system produces recommendations, drafts, summaries, warnings, interpretations, or autonomous actions, the user needs more than a button.

They need ways to:

* understand what is happening
* see why the system thinks something changed
* adjust posture
* express preferences
* change thresholds
* review exceptions
* intervene when needed

This domain holds design work and conceptual writing about interfaces that support judgment.

## What belongs here

This domain can include pieces about:

* decision surfaces
* monitoring controls
* alert preferences
* AI governance interfaces
* confidence and uncertainty displays
* signal interpretation
* posture adjustment
* review queues
* escalation controls
* agent permissions
* model routing
* enterprise AI UX
* interface patterns for supervision
* prototypes and proof-of-concept systems

## Possible artifacts

* Prototype note: “Decision Surface”
* Prototype note: “Monitoring Preferences”
* Prototype note: “AI Resource Control”
* Essay: “The Interface Is a Governance Surface”
* Field report: “Why AI Systems Need Posture Controls”
* Checkpoint: “Current Model of Interfaces for Judgment”

## Why the name works

“Interfaces for Judgment” is stronger and more distinctive than “Design” or “UX.”

It names the deeper purpose of the interface: not just completing a task, but helping a human make or supervise a judgment.

It can hold both practical prototypes and larger theoretical pieces.

It also avoids making the site feel like a conventional portfolio.

## What this domain should avoid

Avoid generic product design writing.

This domain should not become:

* design process case studies
* visual design commentary
* generic UX best practices
* portfolio-style project writeups

The focus should be:

> What kind of interface is needed when the user is not simply acting, but supervising, interpreting, delegating, or governing?

# 5. Media, Memory, and Meaning

## Working description

How ideas become durable through writing, publishing, visual explanation, video, narrative structure, and accumulated archives.

## Why this domain exists

Deep Field Works is both a site and a media-development system.

The website is not only a place to publish finished thoughts.

It is a proving ground for future:

* essays
* videos
* diagrams
* prototypes
* recurring formats
* visual metaphors
* conceptual frameworks

This domain holds the reflective layer about media itself: how ideas are captured, shaped, organized, explained, and revisited over time.

## What belongs here

This domain can include pieces about:

* the site as field journal
* chronological archives
* checkpoints
* public notebooks
* writing as thinking
* turning notes into essays
* turning essays into videos
* visual metaphors
* YouTube formats
* explanatory media
* audience understanding
* narrative structure
* recurring motifs
* creative systems
* publishing without over-polishing

## Possible artifacts

* Essay: “A Field Journal for the AI Age”
* Project log: “Why the Index Is Chronological”
* Note: “The Messiness Is Part of the Point”
* Checkpoint: “What This Site Is Becoming”
* Essay: “The Archive as a Media Engine”
* Video seed: “How Written Models Become Visual Essays”

## Why the name works

“Media, Memory, and Meaning” is intentionally broad.

It can hold writing, publishing, video development, archives, narrative, and reflective project logs.

It also captures a central Deep Field Works idea: the way material is preserved affects what it can later become.

The risk is that the title is more poetic than operational.

That is acceptable because this domain is meant to hold the reflective and media-oriented side of the project.

## What this domain should avoid

Avoid turning this into a meta-blog about blogging.

The deeper question is not:

> How do I publish more content?

The deeper question is:

> How do ideas become durable enough to return to, develop, recombine, and eventually explain to others?

# Optional sections that are not primary domains

## Field Notes

Field Notes should be treated as a content type, not a domain.

Reason:

```text
Domain = what the piece is about
Type = what kind of artifact it is
```

For example:

```text
Domain: Interfaces for Judgment
Type: Field Report
```

A public “Field Notes” section may still be useful as a chronological feed of short observations.

But it should not compete with thematic domains.

---

## Experiments

Experiments should be treated as both:

* a content type
* a top-level navigation section, if prototypes become important

But “Experiments” should not necessarily become a primary domain.

Reason:

Many experiments will fit naturally inside other domains.

Examples:

```text
Monitoring Preferences → Interfaces for Judgment
Agent review flows → Human-Machine Workflows
Recursive knowledge base → Cognitive Infrastructure
Site-generation workflows → Media, Memory, and Meaning
```

A top-level Experiments page can collect them without changing the domain map.

The following names may be useful later, but are not recommended as primary launch domains.

Clear, but too narrow and too operational.

Useful as a project context, but not ideal as a public domain name for Deep Field Works.

Broad and accessible, but too generic.

It risks making the site feel like commentary on AI trends.

---

Strong and accessible, but too narrow for the full project.

It fits some institutional and workflow pieces, but not media, memory, design, or personal cognitive infrastructure.

---

## Agentic Systems

Useful but too technical and potentially dated.

Also risks making the site feel centered on one AI implementation pattern.

---

## Knowledge Work

Accurate but plain.

It may be useful inside essays, but not distinctive enough as a domain.

---

## Sensemaking

Relevant but overused.

It can also feel vague unless grounded carefully.

---

## Design for AI

Too portfolio-like and too narrow.

Deep Field Works includes design, but should not be organized as a UX portfolio.

---

## Governance

Important but too narrow as a standalone domain.

Governance appears inside Human-Machine Workflows, Institutions in Transition, and Interfaces for Judgment.

---

## The Archive

Strong metaphorically, but too narrow alone.

Better as a recurring concept inside Cognitive Infrastructure and Media, Memory, and Meaning.

# Domain page strategy

Each domain page should eventually include:

* a short introduction
* a list of latest pieces in that domain
* recommended starting points
* one current checkpoint
* open questions
* related domains

Suggested structure:

```md
# Cognitive Infrastructure

A short description of the domain.

## Start here

- Featured essay
- Useful note
- Current checkpoint

## Latest entries

Chronological list of recent pieces.

## Current questions

- Question one
- Question two
- Question three

## Related domains

Links to adjacent territories.
```

At launch, these pages can be mostly placeholders.

They should establish the shape of the system without pretending the archive is already mature.

---

# Domain page tone

Domain pages should not sound like marketing pages.

They should sound like maps for an ongoing investigation.

Good:

> This domain tracks how thinking changes when notes, archives, models, and retrieval systems become part of the cognitive loop.

Bad:

> Discover cutting-edge insights into the future of AI-powered cognition.

The reader should feel oriented, not sold to.

---

# Launch visibility decision

The main open decision is whether to expose all five domains immediately or launch with a smaller visible set.

## Option A: show all five at launch

Best if the goal is to reveal the full map early.

Risk:

* some domains may feel thin
* the site may appear larger than it is

## Option B: show three at launch and let others appear later

Best if the site feels too empty with five domain pages.

Risk:

* the larger map remains hidden
* future structure may feel less intentional

## Recommended approach

Create all five domain routes.

Show all five on the Domains page.

Allow some to be marked as emerging if they have little content.

This preserves the larger map without pretending every territory is equally developed.

# How domains may evolve over time

These names should be treated as durable containers, not final answers.

The content inside each domain will likely evolve.

Examples:

* Cognitive Infrastructure may begin with personal knowledge bases, then expand into institutional memory.
* Human-Machine Workflows may begin with agent supervision, then expand into new labor patterns.
* Institutions in Transition may begin with enterprise AI, then expand into schools, governments, or civic systems.
* Interfaces for Judgment may begin with product prototypes, then expand into decision theory and governance patterns.
* Media, Memory, and Meaning may begin with site architecture, then expand into YouTube formats and visual essays.

This is why the names should not be too narrow.

A domain name should still make sense two years from now, even if the first few articles inside it look primitive.

---

# Agent usage rules

When classifying content, agents should:

1. Identify the `documentType`.
2. Identify the primary domain.
3. Assign a theme only after domain and type are clear.
4. Avoid creating new domains without human approval.
5. Prefer existing domains unless the content clearly does not fit.
6. Treat Field Notes and Experiments as types or sections, not domains.
7. Preserve domain stability over short-term precision.

If unsure between two domains, choose the one that best represents the piece’s main contribution.

Example:

A prototype about agent approval thresholds may involve both Human-Machine Workflows and Interfaces for Judgment.

Choose:

```text
Interfaces for Judgment
```

if the main point is the interface pattern.

Choose:

```text
Human-Machine Workflows
```

if the main point is the work model or delegation pattern.

---

# Final principle

Domains are maps, not containers for their own sake.

They should help readers and agents see how the work accumulates.

The structure should make the investigation easier to enter without flattening its chronology.
